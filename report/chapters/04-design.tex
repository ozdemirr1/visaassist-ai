\section{Architecture}
The system starts small and adds a component only together with the feature that needs it
(ADR 0002). The fall prototype consists of a web client, an API with the rule engine, one
PostgreSQL database and an encrypted file store, started together with Docker Compose. After the
advisor meeting of 20 November 2026 it also gets a model client that reads the fields of uploaded
documents with a hosted model (ADR 0007). The job queue, source review, notifications and the
assistant follow in the spring (Figure~\ref{fig:architecture}).

Three simplifications keep the one-person schedule realistic: a small storage interface over a
local volume with application-level encryption instead of an object store, direct pgvector
queries instead of a retrieval framework, and Tesseract as the only OCR engine. Each can be
replaced behind its interface later.

\section{Requirement data and rule schema}
Requirements are data, not code. A destination's rule set is the EU baseline plus one national
layer; every checklist item and rule cites a source passage, and the loader rejects files whose
sources, documents, fields or field types do not match. A \emph{requirement} is a checklist item:
one document, the profiles it applies to and how it is submitted. A \emph{rule} checks the fields
the applicant enters, with a severity and one of twelve check kinds
(Table~\ref{tab:rule-kinds}). Listing~\ref{lst:rule} shows a requirement and the rule that checks
it, both citing the same passage of the EU list \autocite{eu2021harmonised}.

\begin{table}[ht]
  \centering
  \small
  \caption{Check kinds of the rule schema.}
  \label{tab:rule-kinds}
  \begin{tabularx}{\textwidth}{@{}lX@{}}
    \toprule
    Kind & Checks \\
    \midrule
    \texttt{max\_age} & a date field is not older than N months or years at the application date \\
    \texttt{valid\_after\_trip} & a date (passport expiry) is at least N months after the trip ends \\
    \texttt{min\_value}, \texttt{min\_amount} & a number or an amount in a currency reaches a minimum \\
    \texttt{field\_true} & yes/no fields are confirmed (QR code readable, insurance territory) \\
    \texttt{fields\_present} & the listed fields are filled in (contents of the employer letter) \\
    \texttt{period\_covers\_trip} & a period (leave, insurance) covers the whole trip \\
    \texttt{covers\_recent\_months} & a period (bank statement) covers the last N months \\
    \texttt{recent\_monthly\_count} & one document per month for the last N months (payslips) \\
    \texttt{names\_match}, \texttt{values\_match} & fields on other documents equal a reference field \\
    \texttt{translation\_present} & every document not in the listed languages has a translation \\
    \bottomrule
  \end{tabularx}
\end{table}

The current files hold 13 document types, 17 checklist items and 24 rules for the Netherlands and
Norway. For an employed applicant to the Netherlands they give 12 documents and 16 rules; for a
student, 9 documents and 11 rules.

\section{Data model}
The YAML files are the source of truth; the database keeps versioned copies of them so that every
finding can be explained later (Figure~\ref{fig:data-model}). A \emph{requirement set} is one
loaded version of the files, identified by the SHA-256 of their contents. The seed command loads
the files as a set; loading unchanged files again changes nothing, and changed files give a new
set that becomes the only active one, enforced by a partial unique index. Older sets are kept,
because each check run records the set it used. Document types and their fields are versioned
with the set as well, so a renamed field does not change how an earlier finding is shown.

\section{Checklist service}
The request
\begin{center}\texttt{GET /checklist?destination=NL\&profile=employed\&lang=tr}\end{center}
returns the documents and rules
of the active requirement set for one destination and profile (\reqid{FR-02}). Each item carries
the document title in the chosen language, how it is submitted and its citation: the source's
title, publisher and link, the section and the passage, and whether the rule is stated in the
source or derived from it. For Norway the response also reports that documents must be
translated into English or Norwegian. An unknown destination returns 404 with the available
ones; a database without a loaded set returns 503. Thirteen integration tests check the counts
above, the citations, both languages and the error responses against a real PostgreSQL database.

\section{Source monitoring}\label{sec:design-sources}
A snapshot command fetches the five official sources, stores a page only when its SHA-256 has
changed and appends every attempt to a manifest. It was run on 23 October, 5 November and
10 November 2026. Changed pages are reviewed by comparing their visible text and labelled
meaningful, minor or cosmetic; only a meaningful change leads to an edit of the requirement
files, which then produces a new requirement set. In these three runs five pages had a new hash:
three without a visible change and two with a minor one. Detecting meaningful changes
automatically, the administrator's approval and notifying only the application files whose
findings change (\reqid{FR-16}, \reqid{FR-17}) are spring work and the subject of AS3.

The copies of the official pages are kept on the developer's machine; the public repository holds
only the manifest (time, hash, size), because the pages belong to third parties.

\section{AI components and cost}\label{sec:ai-design}
The original plan placed every AI component in the spring. At the meeting of 20 November 2026
the advisor asked for the fall prototype to work with a model already, because a prototype of
this proposal without one would not show its approach. The model choice stays open; the fall uses
a strong hosted model, and the spring moves to the cheapest model that is good enough, preferably
an open model on the project's own server or a server in Türkiye, which also answers the
data-protection question of where personal data may be processed (Chapter~\ref{ch:ethics}).
ADR 0007 records this decision.

\paragraph{Field extraction (fall).} The applicant uploads a document; the model reads the fields
that the document type defines and returns them with the value it found for each. The values are
validated against the field types, like values the applicant types, and shown to the applicant, who confirms or
corrects them before they are stored; the rule engine then decides as before. The model proposes,
the rules decide, and no finding depends on the model's judgement alone. All model calls go
through one client module, so the provider can be replaced without touching the rest of the
system.

\paragraph{What is sent to the model.} In the fall only synthetic documents marked SAMPLE are
sent, from the demo files of Chapter~\ref{ch:evaluation}; no real personal document reaches a
model provider. Masking the fields a check does not need before an external call
(\reqid{NFR-01}) becomes necessary once real documents are allowed, and is spring work.

\paragraph{Cost.} Spending is limited to USD 20 per month (\reqid{NFR-06}): a hard limit in the
provider account, the token count and cost of every call logged, results cached per document, and
no real model call in the automated tests. A cheaper model is used during development and a
stronger one for the measurement and the presentation. With the provider's list prices of
November 2026 and about 2,500 input and 1,500 output tokens per document, the development, three
runs of the comparison of Section~\ref{sec:model-comparison} and the presentation are estimated
at USD 15--18. The estimate is replaced by measured values after the first runs.

\paragraph{Spring.} Document classification, OCR as a fallback, confidence per field with
routing to the applicant, the assistant that answers from source passages, and summaries of
source changes.
