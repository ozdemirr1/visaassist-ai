Three simplifications keep the one-person schedule realistic: a small storage interface over a
local volume with application-level encryption instead of an object store, direct pgvector
queries instead of a retrieval framework, and Tesseract as the only OCR engine. Each can be
replaced behind its interface later.

\section{Requirement data and rule schema}
Requirements are data, not code. A destination's rule set is the EU baseline plus one national
layer; every checklist item and rule cites a source passage, and the loader rejects files whose
sources, documents, fields or field types do not match. A \emph{requirement} is a checklist item:
one document, the profiles it applies to and how it is submitted. A \emph{rule} checks the fields
the applicant enters, with a severity and one of twelve check kinds
(Table~\ref{tab:rule-kinds}). Listing~\ref{lst:rule} shows a requirement and the rule that checks
it, both citing the same passage of the EU list \autocite{eu2021harmonised}.

\begin{table}[ht]
  \centering
  \small
  \caption{Check kinds of the rule schema.}
  \label{tab:rule-kinds}
  \begin{tabularx}{\textwidth}{@{}lX@{}}
    \toprule
    Kind & Checks \\
    \midrule
    \texttt{max\_age} & a date field is not older than N months or years at the application date \\
    \texttt{valid\_after\_trip} & a date (passport expiry) is at least N months after the trip ends \\
    \texttt{min\_value}, \texttt{min\_amount} & a number or an amount in a currency reaches a minimum \\
    \texttt{field\_true} & yes/no fields are confirmed (QR code readable, insurance territory) \\
    \texttt{fields\_present} & the listed fields are filled in (contents of the employer letter) \\
    \texttt{period\_covers\_trip} & a period (leave, insurance) covers the whole trip \\
    \texttt{covers\_recent\_months} & a period (bank statement) covers the last N months \\
    \texttt{recent\_monthly\_count} & one document per month for the last N months (payslips) \\
    \texttt{names\_match}, \texttt{values\_match} & fields on other documents equal a reference field \\
    \texttt{translation\_present} & every document not in the listed languages has a translation \\
    \bottomrule
  \end{tabularx}
\end{table}

The current files hold 13 document types, 17 checklist items and 24 rules for the Netherlands and
Norway. For an employed applicant to the Netherlands they give 12 documents and 16 rules; for a
student, 9 documents and 11 rules.

\section{Data model}
The YAML files are the source of truth; the database keeps versioned copies of them so that every
finding can be explained later (Figure~\ref{fig:data-model}). A \emph{requirement set} is one
loaded version of the files, identified by the SHA-256 of their contents. The seed command loads
the files as a set; loading unchanged files again changes nothing, and changed files give a new
set that becomes the only active one, enforced by a partial unique index. Older sets are kept,
because each check run records the set it used. Document types and their fields are versioned
with the set as well, so a renamed field does not change how an earlier finding is shown.

\section{Checklist service}
\texttt{GET /checklist?destination=NL\&profile=employed\&lang=tr} returns the documents and rules
of the active requirement set for one destination and profile (\reqid{FR-02}). Each item carries
the document title in the chosen language, how it is submitted and its citation: the source's
title, publisher and link, the section and the passage, and whether the rule is stated in the
source or derived from it. For Norway the response also reports that documents must be
translated into English or Norwegian. An unknown destination returns 404 with the available
ones; a database without a loaded set returns 503. Thirteen integration tests check the counts
above, the citations, both languages and the error responses against a real PostgreSQL database.

\section{Source monitoring}
A weekly command fetches the five official sources, stores a page only when its SHA-256 has
changed and appends every attempt to a manifest. Changed pages are reviewed by comparing their
visible text and labelled meaningful, minor or cosmetic; only a meaningful change leads to an
edit of the requirement files, which then produces a new requirement set. In the first three
weeks five pages had a new hash: three without a visible change and two with a minor one.

\section{AI components and cost (spring)}
All model calls go through one client module, and the model of each task is set in configuration
(ADR 0003): a low-cost multimodal model for classification, field extraction, assistant answers
and change summaries; a stronger model as a second pass for uncertain fields; and both models as
the model-only baseline of AS1, so the comparison does not rest on a weak baseline. Spending is
limited to USD 20 per month (\reqid{NFR-06}) by four layers: estimates before each run, a cache of
results, a daily limit in the application and a hard limit in the provider account.
